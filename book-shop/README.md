# ระบบร้านหนังสือ — Next.js + Supabase

ระบบขายหนังสือที่ออกแบบให้เป็น **ศูนย์กลางสต็อก** ไม่ใช่แค่เว็บร้าน
เพราะขายหลายช่องทาง (เว็บ+LINE OA, Shopee, Lazada, หน้าร้าน) แต่ของมีกองเดียว

> **ระบบนี้ไม่คิด VAT** — ราคาที่แสดงคือราคาที่ลูกค้าจ่ายจริง และออก**ใบเสร็จรับเงิน**แทนใบกำกับภาษี

## เริ่มใช้งาน (รันในเครื่องด้วย Docker)

### สิ่งที่ต้องมีก่อน

1. **Node.js** — โหลดจาก [nodejs.org](https://nodejs.org) เลือกตัว **LTS**
2. **Docker Desktop** — โหลดจาก [docker.com](https://www.docker.com/products/docker-desktop)
   → เปิดโปรแกรมทิ้งไว้ รอจนมุมล่างซ้ายขึ้นว่า **Running** สีเขียว

### รันสคริปต์เดียวจบ

**Windows** — เปิด PowerShell ที่โฟลเดอร์ `book-shop` แล้ว:

```powershell
npm.cmd run setup:win
```

> ใช้ `npm.cmd` ไม่ใช่ `npm` เฉยๆ เพราะ PowerShell บล็อกไฟล์สคริปต์ `.ps1` ไว้เป็นค่าเริ่มต้น
> และ npm บน Windows เป็น `npm.ps1` เลยโดนบล็อก — ดูหัวข้อ "แก้ปัญหาที่เจอบ่อย" ถ้าอยากแก้ถาวร
>
> หรือจะ **ดับเบิลคลิกไฟล์ `scripts\setup-local.cmd`** ก็ได้ ไม่ต้องพิมพ์อะไรเลย

**macOS / Linux**:

```bash
npm run setup
```

สคริปต์จะทำให้ทั้งหมดนี้เอง — ติดตั้ง dependency → สร้าง config ของ Supabase →
เปิดฐานข้อมูลใน Docker → สร้างตารางทั้ง 17 migration → ใส่ข้อมูลตัวอย่าง → เขียน `.env.local` ให้

> **ครั้งแรกใช้เวลา 3–8 นาที** เพราะต้องโหลด Docker image ครั้งเดียว ครั้งต่อไปจะเร็วมาก

### เปิดใช้งาน

```powershell
npm.cmd run dev      # Windows  (หรือดับเบิลคลิก scripts\dev.cmd)
```

```bash
npm run dev          # macOS / Linux
```

แล้วเปิด **http://localhost:3000/admin** (หลังบ้าน) หรือ **http://localhost:3000/shop** (หน้าร้าน)

### บัญชีทดสอบ — มีครบทุก role

| role | อีเมล | รหัสผ่าน | เห็นอะไรได้บ้าง |
|---|---|---|---|
| **เจ้าของร้าน** | `owner@bookshop.local` | `bookshop1234` | ทุกอย่าง รวมถึงจัดการสิทธิ์ผู้ใช้ |
| **ผู้จัดการ** | `manager@bookshop.local` | `manager1234` | ทุกอย่างยกเว้นจัดการผู้ใช้ |
| **ฝ่ายสต็อก** | `stock@bookshop.local` | `stock1234` | หนังสือ · รับเข้า · ปรับสต็อก · ออเดอร์ — **ไม่เห็นรายงานกำไร** |
| **ฝ่ายแพ็กของ** | `packer@bookshop.local` | `packer1234` | ออเดอร์กับการจัดส่งเท่านั้น — **ไม่เห็นต้นทุนและสต็อก** |
| **ดูแลลูกค้า** | `support@bookshop.local` | `support1234` | ดูออเดอร์อย่างเดียว แก้อะไรไม่ได้ |
| **ลูกค้า** | `customer@bookshop.local` | `customer1234` | ใช้ที่ `/shop` (หรือเข้า `/shop` เฉยๆ ระบบสร้างลูกค้าทดสอบให้อัตโนมัติ) |

ไม่มีตัวเลขต้นทุนหรือมูลค่าสต็อกเลย และต่อให้ยิง API ตรงก็ไม่ได้ เพราะ RLS ปิดที่ชั้นฐานข้อมูล

ปุ่ม **ออกจากระบบ** อยู่มุมขวาบนถัดจากชื่อผู้ใช้ (หน้าร้านมีปุ่ม "ออก" เล็กๆ ข้างตะกร้า
ซึ่งจะล้างรหัสลูกค้าทดสอบในเครื่องด้วย ทำให้เข้าใหม่เป็นลูกค้าคนละคน — ใช้ทดสอบหลายบัญชีได้)

> รหัสผ่านชุดนี้อยู่ใน `supabase/seed.sql` ซึ่ง **ไม่ถูกส่งขึ้น production**
> ตอนขึ้นเซิร์ฟเวอร์จริงต้องสร้างบัญชีใหม่เอง (ดูหัวข้อ "เมื่อพร้อมขึ้นเซิร์ฟเวอร์จริง")

**Supabase Studio** (ดู/แก้ข้อมูลในตารางตรงๆ) อยู่ที่ http://localhost:54323

## ข้อมูลตัวอย่างที่ใส่มาให้

ตั้งใจใส่ให้ครบทุกกรณีที่อยากให้เห็น ไม่ใช่แค่ข้อมูลสุ่ม

| SKU | หนังสือ | สภาพข้อมูล |
|---|---|---|
| BK-0001 | เมื่อสายลมเปลี่ยนทิศ | **2 ล็อต ต้นทุนต่างกัน** (130 และ 120 บาท/เล่ม) — ไว้ดูการทำงานของ FIFO |
| BK-0003 | คิดช้าเพื่อไปให้ไกล | 1 ล็อต 15 เล่ม |
| BK-0004 | สยามในสายตาชาวต่างชาติ | **เหลือ 2 เล่ม** — ต่ำกว่าจุดสั่งซื้อ จะโผล่ในกล่อง "ต้องสั่งเพิ่ม" |
| BK-0006 | ปลายทางที่ไม่มีชื่อ | **โหมดเปิดจอง** (pre-order) ของเข้าอีก 45 วัน |
| BK-0007 | ตำนานเมืองเก่าที่ถูกลืม | **รับเข้ามา 220 วันแล้วไม่เคยขาย** — ไว้ดูรายงานค้างสต็อก |
| BK-0002, BK-0005 | — | ยังไม่มีสต็อก ไว้ลองกดรับสินค้าเข้าเอง |

### ลองเล่นแบบนี้เพื่อเห็นว่าระบบทำงานยังไง

1. เข้า **หนังสือ → เมื่อสายลมเปลี่ยนทิศ** → ดูตารางล็อต จะเห็นว่าต้นทุนจริงต่างกัน 10 บาท/เล่ม
   ทั้งที่เป็นหนังสือเล่มเดียวกัน เพราะค่าขนส่งขาเข้าเฉลี่ยไม่เท่ากัน
2. เข้า **รับสินค้าเข้า** → กรอกจำนวน/ราคา/ค่าขนส่ง → กล่องสีเขียวจะคำนวณต้นทุนจริงต่อเล่มให้ทันที
   ก่อนกดบันทึก
3. เข้า **ปรับสต็อก** → ใส่ `-3` เหตุผล "ตรวจนับพบขาด" → กลับไปดูหน้ารายละเอียดหนังสือ
   จะเห็นว่าตัดจากล็อตเก่าก่อน และมีบันทึกไว้ในประวัติพร้อมชื่อคนทำ
4. เข้า **สต็อกและต้นทุน** → ดูมูลค่าสต็อกรวมตามราคาทุน
5. เปิด **http://localhost:3000/shop** อีกแท็บ (จะเข้าสู่ระบบเป็นลูกค้าทดสอบอัตโนมัติ)
   → ใส่ตะกร้าทั้งของพร้อมส่งและของ "เปิดจอง" → checkout
   จะเห็นระบบ **แยกเป็น 2 คำสั่งซื้อ** และคิดค่าส่งแยกกัน
6. แนบสลิป (รูปอะไรก็ได้) → กลับมาที่ **หลังบ้าน → คำสั่งซื้อ** → กดยืนยันการชำระเงิน
   → สต็อกถูกตัดแบบ FIFO ต้นทุนถูกล็อกลงออเดอร์ และใบเสร็จออกอัตโนมัติ
7. บันทึกเลขพัสดุพร้อม **ค่าส่งจริง** → ดูกำไรในออเดอร์ลดลงตามจริง
   และรายงาน "ส่วนต่างค่าส่ง" ขึ้นค่าติดลบ
8. **ทดสอบสั่งจอง** — ที่ `/shop` ใส่ตะกร้าเล่ม "ปลายทางที่ไม่มีชื่อ" (เปิดจอง) → checkout → แนบสลิป
   → แอดมินยืนยันเงิน → ออเดอร์ค้างที่ "รอของเข้า" ต้นทุนยังว่าง
   → ไป **รับสินค้าเข้า** กรอกเล่มนั้น → **ระบบจ่ายของให้คิวเองทันที**
   ต้นทุนถูกเติมย้อนหลัง กำไรคำนวณได้ และใบเสร็จออกอัตโนมัติ
9. เข้า **สต็อกและต้นทุน** → เลือกช่วงวันที่ (หรือกดปุ่ม 7/30/90 วัน)
   จะเห็นกราฟแท่งว่าวันไหนขายพุ่ง วันไหนตก และตารางสรุปรายวัน
10. เข้า **รายงานกำไร** → กด **ดาวน์โหลด CSV** ได้ 3 แบบ เปิดใน Excel ภาษาไทยไม่เพี้ยน

## คำสั่งที่ใช้บ่อย

บน Windows ให้ใช้ `npm.cmd` แทน `npm` ทุกคำสั่ง (ดูหัวข้อแก้ปัญหาถ้าอยากแก้ถาวร)

```bash
npm run dev         # เปิดเว็บ
npm test            # ทดสอบตรรกะค่าส่ง/ต้นทุน/กำไร
npm run typecheck   # ตรวจ type

npm run db:reset    # ล้างข้อมูลกลับเป็นค่าเริ่มต้น (ข้อมูลที่กรอกเองจะหายหมด)
npm run db:stop     # หยุดฐานข้อมูล (ปิดเครื่องแล้วเปิดใหม่ต้อง db:start)
npm run db:start    # เปิดฐานข้อมูลอีกครั้ง
npm run db:studio   # ดู URL และ key ทั้งหมดของฐานข้อมูลในเครื่อง
```

## เมื่อพร้อมขึ้นเซิร์ฟเวอร์จริง

สร้าง project ที่ [supabase.com](https://supabase.com) (ฟรี) แล้ว:

```bash
npx supabase login
npx supabase link --project-ref <project-ref>   # ดูจาก URL ของ dashboard
npx supabase db push                            # ส่งเฉพาะ migrations ไม่ส่ง seed
```

**`supabase/seed.sql` ไม่ถูกส่งขึ้น production** — ข้อมูลตัวอย่างและบัญชีทดสอบจึงไม่หลุดไปด้วย
แต่ต้องสร้างบัญชีแอดมินจริงเองที่ Dashboard → Authentication → Users แล้วรัน SQL:

```sql
insert into public.users (auth_user_id, email, display_name)
values ('<auth-uid-จาก-dashboard>', 'you@example.com', 'ชื่อคุณ')
returning id;

insert into public.user_roles (user_id, role_id)
select u.id, r.id from public.users u, public.roles r
where u.auth_user_id = '<auth-uid-จาก-dashboard>' and r.code = 'owner';
```

## สถานะ: ทดสอบการซื้อครบวงจรบนเครื่องจริงแล้ว

รันบน Windows + Docker Desktop เมื่อ 11 ส.ค. 2569 — ไล่ตั้งแต่ลูกค้าหยิบของจนแอดมินส่งพัสดุ

**งวดที่ 1 — สต็อกและต้นทุน**

- migration ทั้ง 17 ไฟล์ + seed ลงครบ ไม่มี error
- หน้าภาพรวมอ่านข้อมูลจริง: 67 เล่ม · มูลค่าทุน ฿8,355.00 (ตรงกับที่คำนวณมือ)
- **FIFO** — ตัด 25 เล่มจากหนังสือที่มี 2 ล็อต ระบบตัดล็อตเก่าหมด 20 เล่ม @฿130
  แล้วต่อด้วยล็อตใหม่ 5 เล่ม @฿120 → COGS ฿3,200 ตรงกับ `tests/money.test.ts`

**งวดที่ 2 — การซื้อครบวงจร**

1. ลูกค้าเข้า `/shop` เข้าสู่ระบบอัตโนมัติ เห็นสต็อกที่หัก safety buffer แล้ว (50 → 49)
2. ใส่ตะกร้า 2 เล่ม (฿590 ส่งฟรี) + สั่งจอง 1 เล่ม (฿320 + ค่าส่ง ฿40)
3. Checkout → **ระบบแยกเป็น 2 ออเดอร์อัตโนมัติ** ของพร้อมส่งไม่ต้องรอของสั่งจอง
4. แนบสลิป → ไฟล์เข้า Supabase Storage แบบปิด แอดมินเปิดดูผ่าน signed URL อายุ 5 นาที
5. แอดมินกดยืนยัน → **ตัดสต็อก FIFO ได้ต้นทุน ฿130/เล่ม · COGS ฿260 · กำไร ฿330**
   และออกใบเสร็จ `RC-2608-000001` อัตโนมัติในทรานแซกชันเดียว
6. บันทึกเลขพัสดุ + ค่าส่งจริง ฿46 → **กำไรลดเหลือ ฿284 ทันที**
   และรายงานส่วนต่างค่าส่งขึ้น −฿46 (เก็บลูกค้า ฿0 เพราะส่งฟรี แต่จ่ายจริง ฿46)

จุดที่ 6 คือเหตุผลที่ต้องบันทึกค่าส่งจริงทุกครั้ง — ถ้าไม่บันทึก กำไรจะดูดีเกินจริง

**งวดที่ 3 — ระบบสั่งจองครบวงจร**

ลูกค้าสั่งจอง 1 เล่ม ฿320 + ค่าส่ง ฿40 → แนบสลิป → แอดมินยืนยัน
→ ออเดอร์ค้างที่ "รอของเข้า" · `unit_cogs` เป็น null (ยังไม่ได้ซื้อของ)
→ รับของเข้า 3 เล่ม @฿200 + ค่าส่งขาเข้า ฿60 → ต้นทุนจริง **฿220/เล่ม**
→ **ระบบจ่ายของให้คิวอัตโนมัติทันที** สถานะเปลี่ยนเป็น "ชำระเงินแล้ว"
→ ต้นทุนถูกเติมย้อนหลังเป็น ฿220 · **กำไร ฿140** · ใบเสร็จออกเอง · คิวว่างเกลี้ยง

## แนวคิดหลักที่ต้องเข้าใจก่อนแก้โค้ด

### 1. ต้นทุนอยู่ที่ "ล็อต" ไม่ใช่ที่ "หนังสือ"

หนังสือเล่มเดียวกันรับเข้าคนละล็อตราคาไม่เท่ากัน ตาราง `purchase_lots` เก็บ

```
landed_unit_cost = unit_cost + (shipping_cost / qty_received)
```

ตอนขายจะตัดจากล็อตเก่าสุดก่อน (FIFO) แล้ว **ล็อกต้นทุนนั้นไว้ใน `order_items.unit_cogs`**
กำไรจึงไม่เพี้ยนย้อนหลังเมื่อราคารับเข้าเปลี่ยน

### 2. FIFO ต้องอยู่ในฐานข้อมูล ห้ามย้ายมา TypeScript

`fn_consume_stock_fifo` ใช้ `SELECT ... FOR UPDATE` ล็อกแถวล็อต
ถ้าย้ายตรรกะมาฝั่ง Node สองออเดอร์ที่เข้าพร้อมกันจะตัดสต็อกซ้อนกันจนติดลบ

### 3. `available_to_sell` ≠ `on_hand`

```
available_to_sell = on_hand − reserved − safety_buffer
```

**ค่าที่ผลักไป Shopee/Lazada คือ `available_to_sell`** ไม่ใช่ `on_hand`
`safety_buffer` (1–2 เล่ม) ยอมเสียโอกาสขายเล็กน้อย เพื่อไม่ให้ oversell แล้วโดนลดคะแนนร้าน

### 4. สิทธิ์บังคับที่ชั้น DB ไม่ใช่แค่ซ่อนปุ่ม

RLS ปิด `purchase_lots` และรายงานกำไรไว้สำหรับผู้ที่ไม่มี `cost.read`
คนแพ็กของยิง API ตรงก็เข้าไม่ได้ — `requirePermission()` เป็นแค่ด่านที่สอง

วิวทุกตัวตั้ง `security_invoker = on` เพราะ Postgres 15+ จะ **ข้าม RLS ของตารางข้างใต้**
ถ้าไม่ตั้ง — ต้นทุนจะรั่วผ่านวิวโดยไม่รู้ตัว

หน้าร้านจึงต้องใช้ `v_public_stock` ที่บอกแค่จำนวนคงเหลือ ไม่เปิดต้นทุน

### 5. สต็อกตัดตอน "ชำระเงินสำเร็จ" ไม่ใช่ตอนกดสั่ง

ระหว่างนั้นใช้ `stock_reservations` ที่หมดอายุใน 30 นาที
ต้องตั้ง cron ยิง `GET /api/cron/expire-reservations` ทุก 5 นาที
(ใส่ header `Authorization: Bearer <CRON_SECRET>`)

### 6. ลูกค้าสร้างออเดอร์เองไม่ได้ ต้องผ่านฟังก์ชัน

`fn_create_orders_from_cart` และ `fn_attach_slip` คิดราคา ค่าส่ง และยอดเงินจากฐานข้อมูลเอง

ถ้าเปิดให้ลูกค้า `insert` ตาราง `orders` ตรงๆ เขาส่ง `total = 0` มาก็ได้
การตรวจในโค้ด Next.js ไม่พอ เพราะลูกค้าถือ session จริงและยิง PostgREST ตรงได้

### 7. วันที่ของล็อตมีสองค่า อย่าสับสน

`purchase_lots.received_at` = **วันที่ของมาถึงร้านจริง** — ใช้เรียงลำดับ FIFO
`purchase_lots.created_at`  = **เวลาที่กดบันทึกเข้าระบบ**

ถ้าบันทึกย้อนหลัง สองค่านี้จะต่างกัน หน้าจอจะขึ้นป้าย "บันทึกย้อนหลัง" ให้เห็น
กราฟความเคลื่อนไหวรายวันใช้ `received_at` สำหรับของรับเข้า ไม่ใช่ `created_at`
ไม่งั้นของที่บันทึกย้อนหลัง 10 ล็อตพร้อมกันจะไปกองรวมอยู่วันเดียว

### 8. Pre-order รู้ต้นทุนทีหลัง ไม่เหมือนการขายปกติ

ตอนลูกค้าจ่ายเงินสั่งจอง เรายังไม่รู้ต้นทุน เพราะยังไม่ได้ซื้อของเข้ามา
`order_items.unit_cogs` จึงเป็น null และออเดอร์ค้างที่สถานะ `preorder_waiting`

`fn_receive_stock` จะเรียก `fn_fulfill_preorders` ให้อัตโนมัติทุกครั้งที่รับของเข้า:
ตัดสต็อก FIFO ตามลำดับคิว → เติม `unit_cogs` ย้อนหลัง → รวม `cogs_total` → ออกใบเสร็จ

**คิวจ่ายเฉพาะคนที่ชำระเงินแล้ว** (`order.status = 'preorder_waiting'`)
คนที่ยังไม่จ่ายจะยังอยู่ในคิวแต่ไม่ได้ของ — ไม่งั้นของจะถูกกันไว้ให้คนที่อาจไม่จ่ายเลย

**ไม่หัก `safety_buffer` ตอนจ่ายให้คิว** เพราะคนสั่งจองคือลูกค้าที่จ่ายเงินมาแล้ว
ต้องได้ก่อนลูกค้าหน้าร้านที่ยังไม่ได้สั่ง

### 9. แจ้งเตือนใช้ trigger ไม่ใช่เรียกจากโค้ดแอป

สถานะออเดอร์ถูกเปลี่ยนจากหลายที่ — ยืนยันเงิน, จ่ายของตามคิว, บันทึกพัสดุ, ยกเลิก
ถ้าให้แต่ละที่เรียก push เอง จะมีวันที่ลืมสักที่แล้วลูกค้าไม่ได้รับแจ้งโดยไม่มีใครรู้

`trg_notify_order_status` จึงเป็นคนบันทึกลงตาราง `notifications` ตอนสถานะเปลี่ยนจริงในฐานข้อมูล
แล้ว cron ค่อยระบายคิว — ส่งพลาดก็ลองใหม่ได้ 3 ครั้ง และเห็นสาเหตุที่เมนู "แจ้งเตือน"

**ใช้ reply ให้มากที่สุด ไม่ใช่ push** — reply (ตอบหลังลูกค้าทัก) ไม่นับโควตา ส่วน push นับ
บอททั้งหมดจึงใช้ reply มีแค่แจ้งเตือนสถานะที่จำเป็นต้อง push

### 10. Webhook ต้องตรวจลายเซ็นก่อนเสมอ

`/api/line/webhook` เปิดสาธารณะ ไม่มี auth อื่นป้องกัน — ลายเซ็น HMAC-SHA256 คือด่านเดียว
ถ้าไม่ตรวจ ใครก็ยิง request ปลอมมาสั่งให้ระบบทำอะไรก็ได้ในนามลูกค้าคนอื่น
และต้องเทียบแบบเวลาคงที่ (`timingSafeEqual`) ไม่ใช่ `===`

### 11. ระวังเงื่อนไขใน ON ของ LEFT JOIN

`... left join orders o on o.id = oi.order_id and o.status = 'paid'`
ไม่ได้กรองแถวทิ้ง แค่ทำให้คอลัมน์ของ `o` เป็น null — `sum(oi.qty)` ยังนับแถวนั้นอยู่
ผลคือออเดอร์ที่ยังไม่จ่ายเงินโผล่เป็นยอดขาย (เจอจริงตอนทดสอบ แก้ใน `0013`)
ใช้ `filter (where o.id is not null)` แทน

## ตั้งค่า LINE (ทำครั้งเดียว)

LINE เรียกเว็บเราจากอินเทอร์เน็ต **`localhost` ใช้ไม่ได้** ต้อง deploy ขึ้น Vercel ก่อน

ต้องมี Supabase บน cloud ก่อน (ฐานข้อมูลใน Docker เข้าถึงจากอินเทอร์เน็ตไม่ได้):

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push        # ส่ง migration ทั้ง 17 ไฟล์ ไม่ส่ง seed
```

จากนั้น import repo เข้า [vercel.com](https://vercel.com) แล้วตั้ง Environment Variables
ให้ครบตาม `.env.example` (ค่า Supabase ใช้ของ cloud ไม่ใช่ของ local)

> `vercel.json` ตั้ง cron ไว้ให้แล้ว — ส่งแจ้งเตือนทุก 1 นาที และปลดล็อกสต็อกค้างทุก 5 นาที

### 2. หาค่า 4 ตัวจาก LINE Developers Console

เข้า [developers.line.biz](https://developers.line.biz/console/)

ระบบใช้ **2 channel** ที่แยกกัน — Messaging API channel คือตัวที่คุยกับลูกค้า
ส่วน LINE Login channel คือตัวที่มี LIFF ค่าจากสองตัวนี้ห้ามสลับกัน

| ตัวแปร | หาที่ไหน |
|---|---|
| `LINE_CHANNEL_SECRET` | **Messaging API** channel → Basic settings → Channel secret |
| `LINE_CHANNEL_ACCESS_TOKEN` | **Messaging API** channel → Messaging API → Channel access token (กด Issue แบบ long-lived) |
| `LINE_LOGIN_CHANNEL_ID` | **LINE Login** channel → Basic settings → Channel ID (ตัวเลขล้วน) |
| `NEXT_PUBLIC_LIFF_ID` | **LINE Login** channel → LIFF → ได้ LIFF ID หน้าตา `2001234567-AbCdEfGh` |

> `LINE_LOGIN_CHANNEL_ID` ใช้ยืนยัน ID token ที่ LIFF ส่งมา ค่า `aud` ในโทเคนคือ ID ของ
> Login channel ไม่ใช่ Messaging API channel — ใส่ผิดจะขึ้น "ตรวจสอบ LINE ID token ไม่ผ่าน"
> โดยไม่บอกสาเหตุ ตอนแรกตัวแปรนี้ชื่อ `LINE_CHANNEL_ID` ซึ่งกำกวมจนชวนใส่ผิด จึงเปลี่ยนชื่อ

ตอนสร้าง LIFF ให้ตั้ง:

- **Endpoint URL**: `https://<โดเมนของคุณ>/shop`
- **Size**: Full
- **Scopes**: เปิด `profile` และ `openid`

## เรื่องความเร็ว

### ทำไมตอน dev ถึงรู้สึกช้า

วัดจริงบนเครื่อง Windows + Docker (ค่ากลางของ 5 ครั้ง หลังคอมไพล์เสร็จแล้ว):

| หน้า | เวลา | อธิบาย |
|---|---|---|
| `/login` | ~34 ms | ไม่ผ่าน middleware ไม่แตะ auth ไม่แตะ DB — นี่คือพื้นของ Next.js dev |
| `/admin/forbidden` | ~138 ms | หน้าเปล่าไม่ดึงข้อมูลอะไรเลย แต่ผ่าน middleware + layout |
| `/admin` | ~198 ms | + 4 query |
| `/admin/stock` | ~260 ms | + 3 query หนัก |

**ตัวถ่วงหลักไม่ใช่ query แต่คือการตรวจตัวตนซ้ำซ้อน** — 104 ms หายไปก่อนดึงข้อมูลแม้แต่แถวเดียว

สาเหตุมี 3 ชั้น:

1. **`getCurrentUser()` ถูกเรียกสองครั้ง** ทั้งใน `layout.tsx` และในหน้า
2. **แต่ละครั้งยิง HTTP 2 รอบ** — ถาม GoTrue ว่าโทเคนนี้เป็นใคร แล้วค่อย query สิทธิ์
3. **middleware ยิงอีกรอบ** เพื่อ refresh session

รวมเป็น **5 รอบ HTTP ไป Docker ต่อการโหลด 1 หน้า** และบน Windows (WSL2)
แต่ละรอบกินเวลา 30–70 ms แทนที่จะเป็นหลักมิลลิวินาที

### แก้ไปแล้ว 3 อย่าง

- **`cache()` ของ React** ครอบ `getCurrentUser` และ `getCustomer`
  เรียกกี่ครั้งใน render เดียวก็ยิงจริงครั้งเดียว (พิสูจน์ด้วย log แล้วว่าเหลือ 1 ครั้ง)
- **`fn_me()`** (migration 0015) ยุบ "ถามว่าใคร + query สิทธิ์" เหลือ RPC เดียว
  ความปลอดภัยเท่าเดิม เพราะ PostgREST ตรวจลายเซ็น JWT ก่อนตั้ง `auth.uid()` ให้
- **Turbopack** ใน `npm run dev` — คอมไพล์ครั้งแรกของแต่ละหน้าเร็วขึ้นมาก

จาก 5 รอบเหลือ **2 รอบ** (middleware 1 + `fn_me` 1)

### สิ่งที่ยังช้าอยู่และเป็นเรื่องปกติ

- **การโหลดครั้งแรกของแต่ละหน้า 800–1900 ms** เพราะ Next.js dev คอมไพล์ตอนเปิดหน้านั้น
  ครั้งต่อไปเร็วขึ้นมาก และ **ตอน production (`npm run build`) ไม่มีขั้นตอนนี้เลย**
- **Docker บน Windows ช้ากว่า Linux** ทุก query ต้องข้าม WSL2
  ขึ้น Supabase cloud จริงแล้วจะเร็วกว่านี้
- ทุกหน้าตั้ง `force-dynamic` เพราะเป็นข้อมูลสด — ถ้าหน้าไหนยอมให้ข้อมูลช้าได้ 30 วินาที
  ใส่ `revalidate` แทนจะเร็วขึ้นอีก

## แก้ปัญหาที่เจอบ่อย

**`npm : File ... npm.ps1 cannot be loaded because running scripts is disabled on this system`**

PowerShell บล็อกการรันไฟล์สคริปต์ `.ps1` ไว้เป็นค่าเริ่มต้น (เป็นการตั้งค่าความปลอดภัยของ Windows
ไม่เกี่ยวกับโปรเจกต์นี้) แก้ได้ 3 ทาง เลือกทางไหนก็ได้:

1. **เติม `.cmd` ต่อท้าย** — ง่ายสุด ไม่ต้องแก้อะไรในเครื่อง

   ```powershell
   npm.cmd run setup:win
   npm.cmd run dev
   ```

2. **ดับเบิลคลิกไฟล์ `.cmd`** — `scripts\setup-local.cmd` แล้ว `scripts\dev.cmd`

3. **แก้ถาวร** — เปิดสิทธิ์รันสคริปต์เฉพาะบัญชีผู้ใช้ของคุณ (ไม่ต้องเป็น Administrator)

   ```powershell
   Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
   ```

   `RemoteSigned` คือค่าที่ Microsoft แนะนำสำหรับเครื่องทั่วไป — สคริปต์ที่เขียนเองในเครื่องรันได้
   ส่วนสคริปต์ที่โหลดมาจากอินเทอร์เน็ตยังต้องมีลายเซ็นดิจิทัล
   ถ้าอยากย้อนกลับภายหลัง: `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy Restricted`

**`supabase start` ล้มด้วย `container is not ready: unhealthy` (analytics / storage / studio)**

คอนเทนเนอร์ analytics ของ Supabase ต้องให้ Docker เปิดพอร์ต `tcp://localhost:2375`
ซึ่งบน Windows ปิดไว้เป็นค่าเริ่มต้น พอมันไม่ขึ้น ตัว storage กับ studio ที่ส่ง log ผ่านมันก็ล้มตาม
แล้ว `supabase start` จะย้อนคืนทั้งชุด

ระบบนี้ไม่ได้ใช้ analytics — สคริปต์ setup ปิดให้อัตโนมัติแล้ว
ถ้าลบ `supabase/config.toml` ทิ้งแล้วสร้างใหม่ ให้แก้เป็น `[analytics] enabled = false` อีกครั้ง

**`permission denied for table users` / เข้า /admin แล้วเด้งกลับหน้า login ทั้งที่ล็อกอินผ่าน**

Postgres มีการควบคุมสิทธิ์ 2 ชั้นที่ต้องผ่านทั้งคู่ — `GRANT` (แตะตารางได้ไหม)
และ `RLS` (แตะได้แล้วเห็นแถวไหน) Supabase รุ่นใหม่ไม่ให้ `GRANT` กับตารางที่สร้างจาก
migration โดยอัตโนมัติอีกแล้ว จึงต้องประกาศเองใน `0010_grants.sql`

ถ้าเพิ่มตารางใหม่แล้วเจอ error นี้ ให้ตรวจว่า `alter default privileges` ใน 0010 ครอบคลุมหรือยัง

**`docker info` ค้าง หรือขึ้น error** — Docker Desktop ยังไม่เปิด หรือเพิ่งเปิดแล้วยังบูตไม่เสร็จ
รอจนไอคอนวาฬนิ่งแล้วลองใหม่

**`supabase start` ค้างนานมากครั้งแรก** — กำลังโหลด image หลาย GB เป็นเรื่องปกติ ปล่อยไว้

**พอร์ตชนกัน (54321/54322/54323)** — มีโปรเจกต์ Supabase อื่นเปิดอยู่
รัน `npx supabase stop --project-id <ชื่ออื่น>` หรือแก้พอร์ตใน `supabase/config.toml`

**เข้า /admin แล้วเด้งกลับหน้า login ตลอด** — `.env.local` ยังไม่มีค่า
รัน `npm run db:studio` ดูค่าแล้วเทียบกับในไฟล์

**หน้า Admin ขึ้นว่าไม่มีสิทธิ์** — บัญชีที่ล็อกอินยังไม่ถูกผูก role
ถ้าใช้บัญชีทดสอบที่ให้มาไม่ควรเจอ — ถ้าสร้างบัญชีเองต้องเพิ่มแถวใน `public.users` + `public.user_roles`

**อยากเริ่มใหม่หมด** — `npm run db:reset`
