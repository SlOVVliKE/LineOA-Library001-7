## 2. ขอบเขตฟีเจอร์

### 2.1 หน้าร้าน (Customer Storefront)

**MVP**

- รายการหนังสือ + ค้นหา (ชื่อ, ผู้แต่ง, ISBN) — Postgres full-text search + `pg_trgm` รองรับพิมพ์ผิด
- กรอง: หมวดหมู่ / สำนักพิมพ์ / ช่วงราคา / สภาพ / **พร้อมส่ง–สั่งจอง–หมด**
- หน้ารายละเอียด: ปก, เรื่องย่อ, ผู้แต่ง, สำนักพิมพ์, ISBN, จำนวนหน้า, ราคา, จำนวนคงเหลือ, **วันที่ของเข้า (ถ้าเป็น pre-order)**
- ตะกร้าผูกกับ `line_user_id` เก็บใน DB
- Checkout: ที่อยู่ → ขนส่ง → ชำระเงิน
- **แยกออเดอร์อัตโนมัติเมื่อตะกร้ามีทั้งของพร้อมส่งและของสั่งจอง** (ไม่ให้ของพร้อมส่งค้างรอ)
- ประวัติคำสั่งซื้อ + สถานะ + ติดตามพัสดุ + ดาวน์โหลดใบเสร็จรับเงิน
- สมุดที่อยู่

**Phase 2+** — รีวิว · Wishlist + แจ้งของเข้า · โค้ดส่วนลด · แนะนำหนังสือเกี่ยวข้อง · **COD**

### 2.2 หลังบ้าน (Admin Backoffice)

**สินค้า** — CRUD + อัปโหลดปก, นำเข้า CSV, **ตั้งโหมดขาย (พร้อมส่ง/สั่งจอง)**, **ผูก SKU กับรายการใน Shopee/Lazada**

**สต็อกและต้นทุน** ← หัวใจของระบบ

- บันทึกล็อตรับเข้า: วันที่, ซัพพลายเออร์, จำนวน, ต้นทุน/เล่ม, ค่าขนส่งขาเข้า
- ต้นทุนต่อหน่วยจริง = (ต้นทุนสุทธิ + ค่าขนส่งเฉลี่ย) ÷ จำนวน
- ตัดสต็อก **FIFO** เมื่อชำระเงินสำเร็จ → บันทึก COGS จริง
- **หน้าจัดการ pre-order**: ดูยอดจองสะสมรายเล่ม, จับคู่กับล็อตที่รับเข้า, ปล่อยของอัตโนมัติตามลำดับการจอง
- ปรับสต็อกด้วยมือ (ของเสีย/หาย/ตรวจนับ) พร้อมเหตุผลและผู้ทำ
- **หน้ากระทบยอดสต็อกข้ามช่องทาง** — เทียบยอดในระบบกับ Shopee/Lazada แจ้งเตือนเมื่อไม่ตรง
- แจ้งเตือนสต็อกต่ำ → push เข้า LINE

**ออเดอร์** — รวมทุกช่องทางในหน้าเดียว, ฟิลเตอร์ตามช่องทาง/สถานะ, ตรวจสลิป, สร้างเลขพัสดุ, พิมพ์ใบปะหน้า, ยกเลิก/คืนเงิน

**เอกสาร** — รายการใบเสร็จรับเงินที่ออก, ยกเลิกใบเสร็จ (void ไม่ลบ), export รายการขายเป็น CSV ให้นักบัญชี

**รายงาน** — ยอดขาย**แยกตามช่องทาง**, กำไรขั้นต้น = ยอดขาย − COGS − ค่าส่งที่จ่ายจริง − **ค่าธรรมเนียม marketplace**, หนังสือขายดี, ค้างสต็อก > 90 วัน, มูลค่าสต็อก, ส่วนต่างค่าส่ง, export CSV/Excel

### สามตารางที่เป็นหัวใจ

**`purchase_lots`** — ต้นทุนอยู่ที่ล็อต ไม่ใช่ที่หนังสือ

```sql
landed_unit_cost = unit_cost + (shipping_cost / qty_received)
```

หนังสือเล่มเดียวกันรับเข้าคนละล็อตราคาไม่เท่ากัน ตอนขายจะตัดจากล็อตเก่าสุดก่อน
แล้ว**ล็อกต้นทุนนั้นไว้ใน `order_items.unit_cogs`** กำไรจึงไม่เพี้ยนย้อนหลังเมื่อราคารับเข้าเปลี่ยน

**`stock_movements`** — บันทึกทุกความเคลื่อนไหว (รับเข้า/ขาย/ปรับ/เสีย/คืน) พร้อมต้นทุน ณ เวลานั้นและชื่อผู้ทำรายการ ตรวจย้อนหลังได้ทุกเล่ม

**`orders.gross_profit`** — generated column คำนวณอัตโนมัติ ไม่มีทางลืมหักค่าใช้จ่าย

```sql
gross_profit = (subtotal - discount)
             - cogs_total
             + shipping_fee            -- ที่เก็บลูกค้า
             - shipping_actual_cost    -- ที่จ่ายขนส่งจริง
             - channel_fee             -- ค่าธรรมเนียม marketplace
```

### กติกาสำคัญ 8 ข้อ

1. **สต็อกตัดตอน "ชำระเงินสำเร็จ" ไม่ใช่ตอนกดสั่ง** — ใช้ `stock_reservations` หมดอายุ 30 นาที + cron เรียก `fn_expire_reservations()`
2. **FIFO ต้องอยู่ในฐานข้อมูล** — `fn_consume_stock_fifo` ใช้ `SELECT ... FOR UPDATE` ล็อกแถวล็อต ถ้าย้ายมาทำใน TypeScript สองออเดอร์ที่เข้าพร้อมกันจะตัดซ้อนกันจนสต็อกติดลบ
3. **`slip_ref` unique** — สลิปเดียวใช้ครั้งเดียว ด่านกันสลิปปลอมที่สำคัญที่สุด
4. **เลขใบเสร็จรันต่อเนื่อง ห้ามข้าม ห้ามลบ** — ใช้ sequence, ยกเลิกด้วย `voided_at` ไม่ใช่ DELETE
5. **`available_to_sell` = on_hand − reserved − safety_buffer** และผลักค่านี้ (ไม่ใช่ `on_hand`) ไปทุกช่องทาง
6. **Pre-order ไม่ตัดสต็อกและยังไม่มี COGS** — `unit_cogs` เติมย้อนหลังเมื่อของเข้าและจับคู่ล็อตแล้ว
7. **`channel_orders.external_order_id` unique** — กัน import ซ้ำเมื่อ webhook ยิงซ้ำ
8. **วิวทุกตัวตั้ง `security_invoker = on`** — ไม่งั้น RLS ของตารางข้างใต้จะถูกข้าม และคนแพ็กของจะเห็นต้นทุนผ่านวิว

### ตัวอย่างการคำนวณกำไร (ทดสอบไว้แล้วใน `tests/money.test.ts`)

```
ล็อต A: 20 เล่ม @120 + ค่าส่งขาเข้า 200  →  ต้นทุนจริง 130.00/เล่ม
ล็อต B: 30 เล่ม @115 + ค่าส่งขาเข้า 150  →  ต้นทุนจริง 120.00/เล่ม

ขาย 25 เล่ม @250 → FIFO ตัดล็อต A 20 เล่ม + ล็อต B 5 เล่ม

ยอดขาย     = 6,250   (ส่งฟรีเพราะเกิน 500)
กำไรขั้นต้น = 3,050   (48.8%)

ออเดอร์เล็ก: 490 บาท + ค่าส่ง 40 (จ่ายขนส่งจริง 45) COGS 260
  ผ่านเว็บเรา   → กำไร 225.00
  ผ่าน Shopee   → กำไร 182.60   (ค่าธรรมเนียม 8% = 42.40)
```

## 4. ค่าส่งและการเชื่อมขนส่ง

### 4.1 กติกาค่าส่ง

```
ยอดสินค้า − ส่วนลด ≥ 500 บาท  →  ค่าส่ง 0 บาท
มิฉะนั้น                     →  ค่าส่ง 40 บาท
```

เก็บ `weight_grams` ทุกเล่มตั้งแต่วันแรก เพราะเมื่อออเดอร์เฉลี่ยหนักขึ้น ค่าส่งจริงจะเกิน 40 บาท และเปลี่ยนไปคิดตามน้ำหนักได้ทันทีโดยแก้แค่ `shipping_rules`

**ต้องเฝ้าดู:** `shipments.actual_cost` เทียบกับ `orders.shipping_fee` — มีรายงานส่วนต่างค่าส่งเฉพาะเรื่องนี้ใน Dashboard

### 4.2 สถาปัตยกรรม Adapter

```ts
// lib/shipping/types.ts
interface CarrierAdapter {
  code: 'flash' | 'jnt'
  estimateRate(input: RateInput): Promise<{ fee: number; etaDays: number }>
  createShipment(order: Order): Promise<{
    trackingNo: string; carrierOrderId: string
    labelUrl: string; cost: number
  }>
  cancelShipment(trackingNo: string): Promise<void>
  parseWebhook(body: unknown, headers: Headers): ShipmentEvent[]
}
```

- **Flash Express** — Open API ที่ `open-api.flashexpress.com` (เอกสาร `open-docs.flashexpress.com`) มี endpoint สร้างออเดอร์, ประเมินค่าส่ง (`/orders/estimate_rate`), Notify API, Webhook พร้อม demo code หลายภาษา และ**รองรับ COD** สำหรับเฟสถัดไป
- **J&T Express** — ต้องติดต่อฝ่ายขายขอ API credential เริ่มตั้งแต่สัปดาห์แรก

**ลำดับ:** Flash ก่อน (สมัครเองได้) → J&T ตามเมื่อได้ credential → ระหว่างรอใช้โหมดกรอกเลขพัสดุเอง

### 4.3 Flow การจัดส่ง

1. Checkout → `estimateRate()` ทั้ง 2 เจ้า แสดงเวลาจัดส่งโดยประมาณ (ลูกค้าจ่าย 40/0 เท่ากัน ส่วนต่างร้านรับ)
2. ชำระเงินสำเร็จ → `createShipment()` ได้เลขพัสดุ + ใบปะหน้า
3. บันทึก `shipments` พร้อม `actual_cost` → push เลขพัสดุเข้า LINE
4. แอดมินพิมพ์ใบปะหน้าจากหน้า Admin (พิมพ์ทีละหลายใบได้)
5. Webhook ขนส่ง → `shipment_events` → เปลี่ยนสถานะ → push LINE เมื่อส่งสำเร็จ

> **ต้อง idempotent** — API ขนส่งอาจ timeout ทั้งที่สร้างสำเร็จ ต้องส่ง merchant reference no. และเช็คก่อนสร้างซ้ำ ไม่งั้นได้เลขพัสดุซ้ำและถูกเรียกเก็บ 2 ครั้ง

## 5. ใบเสร็จรับเงิน (ระบบนี้ไม่คิด VAT)

ราคาที่แสดงคือราคาที่ลูกค้าจ่ายจริง ไม่มีการถอดหรือบวกภาษีในทุกจุดของระบบ

### 5.1 การออกใบเสร็จ

ระบบออก**ใบเสร็จรับเงิน**อัตโนมัติเมื่อยืนยันการชำระเงิน (อยู่ในฟังก์ชัน `fn_confirm_order_paid`)

- เลขที่รูปแบบ `RC-YYMM-NNNNNN` รันต่อเนื่องจาก Postgres sequence
- เก็บ snapshot ชื่อ/ที่อยู่ผู้ขายและผู้ซื้อ ณ วันที่ออก — แก้ข้อมูลร้านภายหลังไม่กระทบใบเก่า
- 1 ออเดอร์ = 1 ใบเสร็จที่ยังไม่ถูกยกเลิก (บังคับด้วย partial unique index)
- **ยกเลิกด้วย `voided_at` ห้าม DELETE** เพื่อให้เลขที่ยังต่อเนื่องและตรวจย้อนหลังได้

**ข้อมูลบนใบเสร็จ** — ชื่อ/ที่อยู่ร้าน, เลขที่ใบเสร็จ, วันที่, ชื่อ/ที่อยู่ผู้ซื้อ, รายการสินค้า (ชื่อ จำนวน ราคาต่อหน่วย), ค่าส่ง, ยอดรวม, วิธีชำระเงิน

**การทำ PDF** — React-PDF หรือ Puppeteer → เก็บใน Supabase Storage (private bucket) → ลูกค้าโหลดผ่าน signed URL อายุจำกัด

### 5.2 ⚠️ สิ่งที่ต้องรู้ก่อนโตขึ้น

การไม่คิด VAT ใช้ได้เมื่อร้านยังไม่ได้จดทะเบียนภาษีมูลค่าเพิ่ม แต่มีสองเงื่อนไขที่ควรจับตา

1. **เกณฑ์บังคับจดทะเบียน** — ผู้ประกอบการที่มีรายรับเกิน **1.8 ล้านบาทต่อปี** ต้องจดทะเบียน VAT ควรตั้งรายงานเตือนเมื่อยอดสะสมเข้าใกล้เกณฑ์
2. **ลูกค้านิติบุคคล** — บริษัทที่ซื้อไปลงบัญชีมักขอใบกำกับภาษี ถ้ากลุ่มนี้เยอะขึ้นอาจต้องพิจารณาจดทะเบียน

**ถ้าวันหนึ่งต้องกลับมาคิด VAT** ระบบต้องเพิ่ม: ฟิลด์สถานะภาษีราย SKU (เพราะตำราเรียนได้รับยกเว้นตาม ม.81(1)(ฉ) แต่นิยายไม่ได้), การถอด VAT ออกจากราคา, ตาราง `tax_invoices` แทน `receipts`, และใบเพิ่มหนี้/ลดหนี้ — **ประมาณ 2 สัปดาห์** ให้ยืนยันกับนักบัญชีเป็นระยะว่ายังไม่ถึงเกณฑ์

> ผมไม่ใช่ที่ปรึกษาภาษี ข้อมูลนี้เป็นจุดตั้งต้นในการปรึกษาผู้เชี่ยวชาญเท่านั้น

## 6. ⚠️ นโยบายการคืนสินค้า — ต้องปรับก่อนใช้จริง

ที่คุณระบุว่า "ไม่สามารถคืนได้เพราะสินค้าอาจไม่เหมือนเดิม" เข้าใจเหตุผลได้ — หนังสือที่ถูกเปิดอ่านแล้วขายต่อไม่ได้ราคาเดิม แต่**นโยบายนี้มีข้อจำกัดทางกฎหมายที่ควรรู้ก่อนประกาศ**

### สิ่งที่กฎหมายไทยกำหนด

การขายออนไลน์เข้าข่าย **"ตลาดแบบตรง"** ตาม พ.ร.บ.ขายตรงและตลาดแบบตรง พ.ศ. 2545 ซึ่ง **มาตรา 33 ให้สิทธิผู้บริโภคบอกเลิกสัญญาภายใน 7 วัน** นับแต่วันที่ได้รับสินค้า และผู้ประกอบการต้อง**คืนเงินเต็มจำนวนภายใน 15 วัน** นับแต่ได้รับหนังสือแสดงเจตนาเลิกสัญญา

นอกจากนี้ ข้อความประเภท "ไม่รับเปลี่ยนหรือคืนสินค้าทุกกรณี" อาจถูกพิจารณาว่าเป็น**ข้อสัญญาที่ไม่เป็นธรรม** ตาม พ.ร.บ.ว่าด้วยข้อสัญญาที่ไม่เป็นธรรม พ.ศ. 2540

> ผมไม่ใช่ทนายความ — ข้อมูลนี้เป็นจุดตั้งต้นให้ปรึกษาผู้เชี่ยวชาญ ไม่ใช่คำแนะนำทางกฎหมาย

### นโยบายที่แนะนำแทน (ป้องกันร้านได้จริงและเสี่ยงน้อยกว่า)

| กรณี | รับคืน? | ใครจ่ายค่าส่งคืน |
|---|:-:|---|
| สินค้าชำรุด/เสียหายจากการขนส่ง | ✓ | ร้าน |
| ส่งผิดเล่ม/ผิดจำนวน | ✓ | ร้าน |
| หนังสือมีตำหนิจากโรงพิมพ์ (หน้าขาด/พิมพ์ซ้ำ) | ✓ | ร้าน |
| เปลี่ยนใจ — **ยังไม่แกะซีล/ไม่มีร่องรอยใช้งาน** | ✓ ภายใน 7 วัน | ลูกค้า |
| เปลี่ยนใจ — แกะแล้ว/มีร่องรอยอ่าน | ✗ | — |
| หนังสือ pre-order ที่ผลิตตามสั่ง | ✗ | — |

**วิธีลดการคืนโดยไม่ต้องห้าม** — รูปสินค้าจริงหลายมุมรวมถึงสันและมุมปก, ระบุสภาพชัดเจน (โดยเฉพาะมือสองในอนาคต), แพ็กกันกระแทกดี (ลดเคสชำรุดซึ่งเป็นเหตุคืนที่พบบ่อยที่สุด), แจ้งวันส่งตามจริง

### สิ่งที่ระบบต้องมีอยู่ดี

ต่อให้ประกาศว่าไม่รับคืน ระบบก็ต้องรองรับการคืนเงินเพราะจะมีเคสสินค้าชำรุดและเคสยกเลิกก่อนส่งแน่นอน:

```sql
returns (
  id uuid pk, order_id uuid fk, order_item_id uuid fk,
  reason text,              -- damaged | wrong_item | defective | cancelled_before_ship | withdrawal_7day
  qty int, condition_on_return text,
  restock_action text,      -- back_to_lot | to_damaged_bin | discard
  refund_amount numeric(12,2),
  refund_receipt_id uuid fk, -- ใบเสร็จคืนเงิน อ้างถึงใบเสร็จเดิม
  approved_by uuid fk, created_at timestamptz
);
```

**สำคัญ:** ของที่คืนกลับมา **ห้ามคืนเข้าล็อตเดิมโดยอัตโนมัติ** ถ้าสภาพเปลี่ยน — ให้เข้า "damaged bin" แล้วให้คนตัดสินใจ ไม่งั้นต้นทุนและสภาพสินค้าในระบบจะเพี้ยน

## 7. การ Sync สต็อกข้ามช่องทาง ← งานที่ยากที่สุดในโปรเจกต์นี้

### 7.1 ปัญหาที่ต้องแก้

ขายเล่มเดียวกันใน 4 ที่ (เว็บเรา, Shopee, Lazada, หน้าร้าน) แต่ของมีกองเดียว ถ้า sync ช้าหรือพลาด จะเกิด **overselling** — ขายของที่ไม่มี ต้องยกเลิกออเดอร์ ซึ่งใน Shopee/Lazada มีบทลงโทษ (คะแนนร้านตก, ถูกจำกัดการมองเห็น, ในกรณีร้ายแรงถูกระงับร้าน)

### 7.2 ทางเลือก: เขียนเอง vs ใช้ผู้ให้บริการ

| | เขียน API เอง | ใช้ระบบสำเร็จรูป |
|---|---|---|
| เวลาพัฒนา | +4–6 สัปดาห์ | +3–5 วัน |
| ค่าใช้จ่าย | 0/เดือน (แต่ค่าแรงสูง) | ~1,000–3,000 บาท/เดือน |
| ควบคุมได้ | เต็มที่ | จำกัดตามที่ผู้ให้บริการเปิด |
| ดูแลต่อ | ต้องตาม API ที่เปลี่ยนเอง | ผู้ให้บริการดูแล |
| ต้นทุน/กำไร | อยู่ในระบบเราครบ | มักต้อง export มารวมเอง |

ผู้ให้บริการในไทยที่เชื่อม Shopee/Lazada/TikTok Shop/LINE OA ผ่าน API ทางการมีหลายเจ้า เช่น Seller Pao และ OneCart — เมื่อออเดอร์เข้ามาจากช่องทางใด ระบบจะตัดสต็อกและอัปเดตทุกช่องทางทันที

**คำแนะนำ:** ระบบต้นทุนและกำไรที่คุณต้องการนั้น**ไม่มีเจ้าไหนทำได้ครบ** (โดยเฉพาะ FIFO รายล็อตพร้อมค่าขนส่งขาเข้าเฉลี่ย) ทางที่สมเหตุสมผลที่สุดคือ **ไฮบริด**:

- ใช้ระบบสำเร็จรูปเป็นตัว sync สต็อกกับ marketplace ในช่วงแรก (เร็ว ลดความเสี่ยง oversell ทันที)
- ระบบเราเป็นเจ้าของข้อมูลต้นทุน กำไร และภาษี — ดึงออเดอร์จากตัว sync เข้ามาบันทึกอีกที
- ถ้ายอดโตจนค่าบริการรายเดือนแพงกว่าค่าดูแลโค้ด ค่อยเขียน adapter เองแทน

> ต้องตัดสินใจข้อนี้ก่อนเริ่มเฟส 6 เพราะมีผลต่อ timeline 4–6 สัปดาห์

### 7.3 ถ้าเลือกเขียนเอง — สถาปัตยกรรม

```ts
// lib/channels/types.ts
interface ChannelAdapter {
  code: 'shopee' | 'lazada'
  pushStock(sku: string, qty: number): Promise<void>
  pushPrice(sku: string, price: number): Promise<void>
  pullOrders(since: Date): Promise<ExternalOrder[]>
  getStock(sku: string): Promise<number>          // ใช้กระทบยอด
  parseWebhook(body: unknown, headers: Headers): ChannelEvent[]
}
```

**หลักการ 6 ข้อ**

1. **ระบบเราเป็น SSOT** — ห้ามแก้สต็อกใน Shopee/Lazada ด้วยมือเด็ดขาด มิฉะนั้นข้อมูลจะแตกทันที (ต้องตกลงกับทีมงานให้ชัด)
2. **ผลัก `available_to_sell` ไม่ใช่ `on_hand`** — หักของที่จองไว้และ safety buffer ออกก่อนเสมอ
3. **Safety buffer 1–2 เล่ม/SKU** สำหรับเล่มที่ขายดี — ยอมเสียโอกาสขายเล็กน้อย ดีกว่าโดนลงโทษจาก oversell
4. **คิวงานแบบ debounce** — ขาย 5 ออเดอร์ใน 1 นาที ไม่ควรยิง API 5 ครั้ง รวมเป็นครั้งเดียว ป้องกัน rate limit
5. **Retry แบบ exponential backoff + dead letter** — API marketplace ล่มบ่อย งานที่ fail ต้องไม่หายเงียบ
6. **กระทบยอดทุกคืน** — ดึงสต็อกจริงจากทุกช่องทางเทียบกับระบบเรา ลงตาราง `sync_discrepancies` แล้ว push แจ้งเตือนเข้า LINE ถ้าไม่ตรง

**ข้อควรรู้ทางเทคนิค** — Shopee Open Platform ใช้ HMAC-SHA256 signature ทุก request และมีระบบ token ที่ต้องต่ออายุ ส่วน Lazada Open Platform มีการปิดบังข้อมูลผู้ซื้อ (buyer data masking) ซึ่งกระทบการออกใบเสร็จและการติดต่อลูกค้า — ต้องออกแบบให้รองรับกรณีไม่มีชื่อ/ที่อยู่เต็ม

### 7.4 หน้าร้าน (offline)

ช่องทางนี้ sync อัตโนมัติไม่ได้ ต้องมีหน้าจอ "ขายหน้าร้าน" ใน Admin: สแกน/เลือกเล่ม → บันทึกการขาย → ตัดสต็อกทันที → ผลักยอดใหม่ออกทุกช่องทาง เป็นงานเล็กแต่ขาดไม่ได้ ไม่งั้นสต็อกจะเพี้ยนทุกวัน

## 8. ระบบ Pre-order

### 8.1 โหมดการขาย 3 แบบ

| โหมด | เงื่อนไข | ลูกค้าเห็น |
|---|---|---|
| `stock` | มีของพร้อมส่ง | "พร้อมส่ง (เหลือ 5 เล่ม)" |
| `preorder` | ยังไม่มีของ รู้วันของเข้า | "เปิดจอง — ของเข้า 15 ก.ย. 2026" |
| `backorder` | ของหมดชั่วคราว รอเติม | "สินค้าหมด — สั่งจองได้ ส่งภายใน 14 วัน" |

### 8.2 Flow

1. ลูกค้าเลือกเล่มที่เปิดจอง → ระบบเช็ค `preorder_limit` ว่ายังรับได้ไหม
2. **ถ้าตะกร้ามีทั้งของพร้อมส่งและของจอง → แยกเป็น 2 ออเดอร์อัตโนมัติ** ไม่ให้ของพร้อมส่งค้างรอ (และคิดค่าส่งแยก 2 ครั้ง — ต้องแจ้งลูกค้าให้ชัดที่หน้า checkout)
3. ชำระเงิน: เต็มจำนวน หรือมัดจำตาม `preorder_deposit_pct`
   - รับมัดจำ → ออกใบเสร็จของยอดมัดจำ · เก็บส่วนที่เหลือตอนของเข้า → ออกใบเสร็จอีกใบ
4. เข้าคิว `preorder_queue` เรียงตาม `queued_at` — **ใครจองก่อนได้ก่อน**
5. ของเข้า → บันทึกล็อต → ระบบจ่ายของตามคิวอัตโนมัติ:
   - เติม `unit_cogs` ย้อนหลังจากล็อตที่รับเข้าจริง ← ตรงนี้คือจุดที่ pre-order ต่างจากการขายปกติ
   - ถ้าของเข้าไม่พอทั้งคิว → จ่ายตามลำดับ ที่เหลือคงสถานะ `waiting`
   - เก็บส่วนที่เหลือ (ถ้าจ่ายมัดจำ) → push LINE แจ้งเก็บเงิน
6. Push LINE: "หนังสือที่คุณจองเข้าแล้ว" → จัดส่ง

### 8.3 ประเด็นที่ต้องระวัง

- **ของไม่เข้าตามกำหนด** — ต้องมีปุ่มเลื่อนวันพร้อม broadcast แจ้งทุกคนในคิว และ**ต้องให้ลูกค้ายกเลิกและขอเงินคืนได้** (สินค้าไม่ได้ส่งตามสัญญา)
- **จองแล้วไม่จ่าย** — ตั้ง TTL ยาวกว่าออเดอร์ปกติ (เช่น 24–48 ชม.) เพราะยอดสูงกว่า
- **ห้ามให้ pre-order กินสต็อกจริง** — `preorder_queue` แยกจาก `stock_reservations` โดยสิ้นเชิง
- **สินค้าจองใน marketplace** — Shopee/Lazada มีระบบ pre-order ของตัวเองที่กติกาต่างกัน อาจต้องจำกัดให้เปิดจองเฉพาะช่องทางเราในช่วงแรก
- **กำไรของ pre-order รู้ทีหลัง** — รายงานต้องแยกให้ชัดว่าออเดอร์ไหน COGS ยังไม่สมบูรณ์ ไม่งั้นตัวเลขกำไรระหว่างเดือนจะบวมเกินจริง

## 9. COD (เตรียมโครงไว้ ยังไม่ทำ)

ยังไม่พัฒนาในเฟสนี้ แต่ schema รองรับแล้ว (`orders.payment_type`, `cod_amount`, `cod_remittance_id`, `shipments.cod_amount`) เมื่อจะเปิดใช้ต้องเพิ่ม:

- ตาราง `cod_remittances` — รอบโอนเงินกลับจากขนส่ง (Flash/J&T โอนเป็นรอบ ไม่ใช่ทันที)
- หน้ากระทบยอด: เทียบยอด COD ที่ควรได้ vs ที่ได้จริง หักค่าธรรมเนียม COD (~2–3%)
- สถานะออเดอร์เพิ่ม: `cod_pending_remittance` → `cod_settled`
- นโยบายลูกค้าปฏิเสธรับของ — ใครรับค่าส่งขากลับ, ตัดสินใจว่าจะจำกัด COD เฉพาะลูกค้าที่เคยซื้อสำเร็จแล้วไหม

> COD ในไทยมีอัตราปฏิเสธรับของสูงกว่าจ่ายล่วงหน้ามาก ควรเปิดใช้เมื่อมีข้อมูลลูกค้าประจำแล้ว

### ความปลอดภัยที่ต้องทำ

- **RLS ทุกตาราง** — ลูกค้าเห็นเฉพาะข้อมูลตัวเอง; `purchase_lots`, `stock_movements.unit_cost`, รายงานกำไร เปิดเฉพาะผู้มี `cost.read`
- ตรวจสิทธิ์ที่ **ชั้น DB** ไม่ใช่แค่ซ่อน UI
- **Verify signature ทุก webhook** — LINE (`x-line-signature` HMAC-SHA256), ขนส่ง, Shopee (HMAC-SHA256), Lazada
- **Validate LIFF ID token ฝั่ง server** — ห้ามเชื่อ `line_user_id` จาก client
- Service role key และ credential ของ marketplace อยู่ฝั่ง server เท่านั้น
- คำนวณราคาและค่าส่งทั้งหมดฝั่ง server
- **Audit log** ทุกการแก้ต้นทุน สิทธิ์ การยกเลิกใบเสร็จ และการปรับสต็อกด้วยมือ

## 13. ความเสี่ยงและวิธีรับมือ

| ความเสี่ยง | ผลกระทบ | วิธีรับมือ |
|---|---|---|
| **Oversell ข้ามช่องทาง** | ยกเลิกออเดอร์ · คะแนนร้านตก · ถูกจำกัดการมองเห็น | SSOT เดียว · ผลัก `available_to_sell` · safety buffer 1–2 เล่ม · กระทบยอดรายคืน · **ห้ามแก้สต็อกในแอป marketplace ด้วยมือ** |
| **นโยบายไม่รับคืนขัดกฎหมาย** | ถูกร้องเรียน สคบ. · เสียชื่อเสียง | ใช้นโยบายตามหัวข้อ 6 · ปรึกษาทนาย · ระบบรองรับ return + ใบลดหนี้อยู่แล้ว |
| **ไม่บันทึกค่าธรรมเนียม marketplace** | ไม่รู้ว่าช่องทางไหนขาดทุน | `orders.channel_fee` บังคับกรอก · รายงานกำไรแยกช่องทาง |
| **ยอดขายทะลุ 1.8 ล้าน/ปี** | ต้องจดทะเบียน VAT ย้อนหลัง | ตั้งรายงานเตือนเมื่อยอดสะสมเข้าใกล้เกณฑ์ · เผื่อเวลาแก้ระบบ 2 สัปดาห์ |
| **ของ pre-order ไม่เข้าตามกำหนด** | ลูกค้าเสียความเชื่อมั่น · ต้องคืนเงินจำนวนมาก | รับจองเฉพาะเล่มที่ยืนยันกับสำนักพิมพ์แล้ว · ปุ่มเลื่อนวัน + broadcast · ให้ยกเลิกได้ |
| เลขใบเสร็จข้าม/ซ้ำ | เอกสารไม่ต่อเนื่อง ตรวจสอบยาก | sequence + partial unique index · void ห้ามลบ |
| สลิปปลอม/สลิปซ้ำ | สูญเงิน + ของหาย | `slip_ref` unique + ตรวจยอด/บัญชี/เวลา + เศษสตางค์สุ่ม |
| สต็อกติดลบเมื่อซื้อพร้อมกัน | ขายของที่ไม่มี | Transaction + row lock + reservation 30 นาที |
| ค่าส่งจริงเกิน 40 บาท | กำไรหดเงียบๆ | บันทึก `actual_cost` ทุกพัสดุ · รายงานส่วนต่าง · สลับเป็นคิดตามน้ำหนักได้ |
| API ขนส่ง/marketplace timeout | เลขพัสดุซ้ำ · ออเดอร์ import ซ้ำ | Idempotency key + unique constraint + retry with backoff |
| **J&T / Shopee / Lazada อนุมัติ API ช้า** | เฟส 5–6 ล่าช้า | เริ่มติดต่อสัปดาห์ที่ 1 · Flash ก่อน · fallback กรอกเองได้ |
| Lazada masking ข้อมูลผู้ซื้อ | ออกใบเสร็จ/ติดต่อลูกค้าไม่ได้ | ออกแบบให้รองรับข้อมูลไม่ครบ · ใช้ช่องทางแชทของ Lazada แทน |
| แอดมินเห็นข้อมูลเกินสิทธิ์ | ต้นทุนรั่ว | บังคับที่ RLS · ทดสอบทุก role ก่อนเปิด |
| โควตาข้อความ LINE บาน | ค่าใช้จ่ายพุ่ง | ใช้ reply แทน push · รวมแจ้งเตือน · ตั้งเพดานเตือน |
| ต้นทุนบันทึกไม่ครบ | รายงานกำไรเชื่อไม่ได้ | บังคับกรอกตอนรับเข้า · ตรวจนับสต็อกรายเดือน |
| LIFF ใช้ได้เฉพาะในแอป LINE | ลูกค้าเดสก์ท็อปเข้าไม่ได้ | ทำเว็บเปิดนอก LINE ได้ (fallback LINE Login) |

## 15. คำถามที่ยังเปิดอยู่

1. **PDPA** — เก็บข้อมูลลูกค้าจากหลายช่องทาง ต้องมี privacy policy + ระบบให้ลูกค้าขอลบข้อมูล ทำในเฟสไหน?
